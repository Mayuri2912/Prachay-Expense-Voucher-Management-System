# Database Schema

Database: **MySQL 8.0** (8.0.16 or newer, because CHECK constraints are enforced from that version).
Default database name: `prachay_expense_vouchers` · Character set: `utf8mb4` · Engine: InnoDB.

| File | Purpose |
|---|---|
| [`database/schema.sql`](../database/schema.sql) | Creates the database and the four tables (drops them first) |
| [`database/seed.sql`](../database/seed.sql) | Development demo data: 5 users, 14 vouchers and their history |

Run both with `npm run db:setup` (first time) or `npm run db:reset` (wipe and reload).

---

## Relationships

```
┌──────────────┐  1        many  ┌──────────────────────┐  1      many  ┌───────────────────┐
│    users     │────────────────<│       vouchers       │──────────────<│  voucher_history  │
│              │  employee_id    │                      │  voucher_id   │                   │
│ id (PK)      │                 │ id (PK)              │               │ id (PK)           │
│ email (UQ)   │  1        many  │ voucher_number (UQ)  │               │ voucher_id (FK)   │
│ role         │────────────────<│ employee_id (FK)     │               │ performed_by (FK) │
│ ...          │  reviewed_by    │ reviewed_by (FK)     │               │ ...               │
└──────┬───────┘                 └──────────────────────┘               └─────────┬─────────┘
       │ 1                                                                        │ many
       └──────────────────────────────────────────────────────────────────────────┘
                                   performed_by

┌────────────────────┐
│ voucher_sequences  │   stand-alone: one counter row per year
│ seq_year (PK)      │
│ last_number        │
└────────────────────┘
```

- One **user** (an employee) creates many **vouchers** - `vouchers.employee_id`.
- One **user** (a director) reviews many **vouchers** - `vouchers.reviewed_by`.
- One **voucher** has many **history** rows - `voucher_history.voucher_id`.
- One **user** performs many **history** actions - `voucher_history.performed_by`.

## Table: `users`

Everyone who can log in.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INT UNSIGNED, auto increment | no | Primary key |
| `full_name` | VARCHAR(100) | no | Shown as "Employee Name" on vouchers |
| `email` | VARCHAR(150) | no | **Unique** - the login name |
| `password_hash` | VARCHAR(255) | no | bcrypt hash. The plain password is never stored. |
| `role` | ENUM('EMPLOYEE','DIRECTOR','ACCOUNTS') | no | Decides what the user may do |
| `employee_code` | VARCHAR(20) | yes | **Unique**. The optional "Employee ID" (for example `EMP-101`) |
| `department` | VARCHAR(100) | yes | The user's own department; pre-fills the voucher form |
| `is_active` | TINYINT(1) | no | Default 1. 0 = the account is disabled and cannot log in |
| `created_at` | TIMESTAMP | no | Set automatically |
| `updated_at` | TIMESTAMP | no | Updated automatically on every change |

Keys: `PRIMARY KEY (id)`, `UNIQUE (email)`, `UNIQUE (employee_code)`.

## Table: `vouchers`

One row per expense voucher. The comments in the middle column map each column to the voucher details listed
in the assignment.

| Column | Type | Null | Assignment field / notes |
|---|---|---|---|
| `id` | INT UNSIGNED, auto increment | no | Primary key |
| `voucher_number` | VARCHAR(20) | no | **Voucher Number** - unique, generated by the server (`EV-2026-00015`) |
| `employee_id` | INT UNSIGNED | no | FK → `users.id`. Gives the **Employee Name** and **Employee ID** through a JOIN |
| `voucher_date` | DATE | no | **Voucher Date** |
| `expense_date` | DATE | no | **Expense Date** |
| `department` | VARCHAR(100) | no | **Department Name** |
| `expense_title` | VARCHAR(150) | no | **Expense Title** |
| `expense_category` | VARCHAR(50) | no | **Expense Category** |
| `expense_description` | TEXT | yes | **Expense Description** |
| `amount` | DECIMAL(12,2) | no | **Amount** - exact decimal, must be greater than 0 |
| `employee_signature_path` | VARCHAR(255) | yes | **Employee Signature** - path of the image inside `server/uploads` |
| `status` | ENUM('DRAFT','PENDING_APPROVAL','APPROVED','REJECTED') | no | **Current Status**, default `DRAFT` |
| `submitted_at` | TIMESTAMP | yes | When the employee submitted it |
| `reviewed_by` | INT UNSIGNED | yes | FK → `users.id`. The director who approved or rejected |
| `director_signature_path` | VARCHAR(255) | yes | **Director Signature** |
| `approved_at` | TIMESTAMP | yes | **Approval Date** |
| `rejected_at` | TIMESTAMP | yes | When it was rejected |
| `rejection_reason` | VARCHAR(500) | yes | **Rejection Reason** |
| `created_at` | TIMESTAMP | no | **Created Date** - set automatically |
| `updated_at` | TIMESTAMP | no | **Last Updated Date** - updated automatically |

### Keys and indexes

| Name | Columns | Why |
|---|---|---|
| `PRIMARY` | `id` | Row identity |
| `uq_vouchers_number` | `voucher_number` | **Business rule: every voucher number is unique** |
| `idx_vouchers_employee_status` | `employee_id, status` | "My vouchers" list and the employee dashboard |
| `idx_vouchers_status` | `status` | Pending / approved lists and dashboards |
| `idx_vouchers_expense_date` | `expense_date` | Date-range filter and sorting |
| `idx_vouchers_department` | `department` | Department filter |
| `idx_vouchers_category` | `expense_category` | Category filter |
| `idx_vouchers_created_at` | `created_at` | Default sort order (newest first) |
| `fk_vouchers_employee` | `employee_id` → `users.id` | A voucher always belongs to a real user; a user with vouchers cannot be deleted |
| `fk_vouchers_reviewer` | `reviewed_by` → `users.id` | The reviewer is a real user |

### CHECK constraints

The application validates everything first. These constraints are a last line of defence: even a bug in the
code, or someone editing the database by hand, cannot store a voucher that breaks the rules.

| Constraint | Rule |
|---|---|
| `chk_vouchers_amount_positive` | `amount > 0` |
| `chk_vouchers_submitted_has_employee_signature` | Any voucher that is not a draft must have an employee signature |
| `chk_vouchers_approved_has_director_signature` | An approved voucher must have a Director signature and an approval date |
| `chk_vouchers_rejected_has_reason` | A rejected voucher must have a rejection reason and a rejection date |

## Table: `voucher_history`

Audit trail: one row every time something happens to a voucher. It is written in the **same transaction**
as the change itself, so the history can never disagree with the voucher.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INT UNSIGNED, auto increment | no | Primary key |
| `voucher_id` | INT UNSIGNED | no | FK → `vouchers.id`, `ON DELETE CASCADE` |
| `action` | ENUM('CREATED','UPDATED','SUBMITTED','APPROVED','REJECTED') | no | What happened |
| `from_status` | ENUM (the four statuses) | yes | Status before (NULL when created) |
| `to_status` | ENUM (the four statuses) | no | Status after |
| `performed_by` | INT UNSIGNED | no | FK → `users.id`. Who did it |
| `remarks` | VARCHAR(500) | yes | The rejection reason, for a `REJECTED` row |
| `created_at` | TIMESTAMP | no | When it happened |

Indexes: `idx_history_voucher (voucher_id, created_at)` for the timeline on the voucher page, and
`idx_history_created_at (created_at)` for "Recent Voucher Activity" on the Director dashboard.

`ON DELETE CASCADE`: only drafts can be deleted, and a draft's history (created / edited) is removed with it.

## Table: `voucher_sequences`

A tiny counter table used to generate voucher numbers.

| Column | Type | Notes |
|---|---|---|
| `seq_year` | SMALLINT UNSIGNED | Primary key - the year |
| `last_number` | INT UNSIGNED | The last number handed out in that year |

How a number is generated (inside the transaction that creates the voucher):

```sql
INSERT INTO voucher_sequences (seq_year, last_number) VALUES (2026, 1)
  ON DUPLICATE KEY UPDATE last_number = last_number + 1;
SELECT last_number FROM voucher_sequences WHERE seq_year = 2026;   -- e.g. 15  ->  EV-2026-00015
```

The first statement locks the year's row until the transaction ends. If two employees create a voucher at the
same moment, the second one waits for the first, so both receive different numbers. The UNIQUE key on
`vouchers.voucher_number` guarantees it a second time. The counter restarts from 1 each year.

## Design notes

**Normalisation.** Each fact is stored once. The employee's name and employee ID live in `users`; vouchers only
hold `employee_id`. The same goes for the reviewer.

**Money.** `DECIMAL(12,2)` stores amounts exactly (up to 9,999,999,999.99). Floating-point types would cause
rounding errors. The `mysql2` driver returns DECIMAL values as strings (`"4850.00"`), so nothing is rounded on
the way to the browser.

**Status.** An `ENUM` with exactly four values, used with the same names in the database, the backend, the
frontend, the filters and the dashboards.

**Time.**

- Moments in time (`created_at`, `updated_at`, `submitted_at`, `approved_at`, `rejected_at`) are `TIMESTAMP`
  columns. MySQL stores them in UTC. The API's connections run with `time_zone = '+00:00'`, so the API always
  reads and writes UTC and sends ISO strings such as `2026-10-10T15:21:07.000Z`. The browser converts them to
  the user's local time for display.
- Plain calendar dates (`voucher_date`, `expense_date`) are `DATE` columns and are returned as `YYYY-MM-DD`
  text, so a time zone can never move them to another day.
- "Approved today" on the Director dashboard compares `approved_at` with the start of today in the office time
  zone (`APP_TIMEZONE_OFFSET` in `.env`).

**Files.** Signature images are stored on disk under `server/uploads/`. The database holds only a relative
path (`signatures/employee-1760109582000-9f2c4b1a7d3e5f60.png`). File names are generated by the server.
The demo images used by the seed data are in `server/uploads/seed/`.

**SQL injection.** All queries use `?` placeholders through `mysql2` prepared statements. The only dynamic
parts of a query are column names for sorting, and those come from a fixed list in the code.

**Preserving the employee's entries.** The approve and reject statements only write `status`, `reviewed_by`,
`director_signature_path`, `approved_at`, `rejected_at` and `rejection_reason`. The columns the employee
filled in are never part of those updates.

## Seed data

`database/seed.sql` is for **local development only**.

| Data | Details |
|---|---|
| Users | 1 Director, 1 Accounts user, 3 Employees - all with the same demo password (bcrypt hashes, see README) |
| Vouchers | 14: 3 Draft, 4 Pending Approval, 5 Approved, 2 Rejected |
| History | Matching created / submitted / approved / rejected rows |
| Sequence | Counter set to 14, so the next voucher created in the app is number 15 |

All dates are written relative to the day the seed runs (`CURDATE() - INTERVAL 5 DAY`, `NOW() - INTERVAL 10 MINUTE` …),
so "Approved today", "Rejected today" and "Recent activity" always have something to show.

## Useful queries

```sql
-- How many vouchers are in each status, and what they add up to
SELECT status, COUNT(*) AS vouchers, SUM(amount) AS total
  FROM vouchers GROUP BY status;

-- Every voucher with its employee and reviewer
SELECT v.voucher_number, e.full_name AS employee, v.amount, v.status, r.full_name AS reviewed_by
  FROM vouchers v
  JOIN users e ON e.id = v.employee_id
  LEFT JOIN users r ON r.id = v.reviewed_by
 ORDER BY v.created_at DESC;

-- The full history of one voucher
SELECT h.created_at, h.action, h.from_status, h.to_status, u.full_name, h.remarks
  FROM voucher_history h
  JOIN users u ON u.id = h.performed_by
 WHERE h.voucher_id = 1
 ORDER BY h.created_at;
```
